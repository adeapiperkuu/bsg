## 1. The system as it stands today

Four login roles, enforced by `require_role(...)` at the route layer and by Postgres Row-Level Security at the database layer:

| Role | Who | DB-layer scope |
|---|---|---|
| `client` | External stakeholders | Own org, and (per application code) own **assigned projects** only |
| `delivery_manager` | PM / Delivery Lead / QA Lead / Ops Manager / Resource Manager | Full read/write, own org |
| `bsg_leadership` | BSG HQ | Read-only, all orgs |
| `super_admin` | Platform admin | Full CRUD on `organisations`, `users`, `metric_configurations`; no special access to client operational data |

Plus `service_role` — a non-login backend credential (`SUPABASE_SERVICE_ROLE_KEY`) that bypasses RLS entirely and is used for ingestion and agent writes.

Already built and working:
- `require_role()` dependency (`backend/app/core/security.py:117`) gating every route.
- Full user management UI with an organisation picker (`frontend/src/routes/admin.users.tsx`, 708 lines — list, create, edit, deactivate, filter by org/role/status).
- An RLS policy baseline covering the 19 Phase‑1 tables (`supabase/migrations/20260623100000_rls_policies.sql`).
- A `project_assignments` table and app-layer scoping helpers (`backend/app/services/scoping.py`) that restrict `client` users to specific projects within their org — a finer-grained model than either design doc (`10. DB Schema.md`, `13. Security & Compliance.md`) describes.

This plan closes the gaps between those pieces.

## 2. Verified findings, ranked by severity

### P0 — Correctness / security bugs

**F1. RLS does not enforce project-assignment scoping for `client` — only the application layer does.**
`backend/app/services/scoping.py:15-43` restricts a `client` user to projects they have an active row in `project_assignments` for. But every `client`-role RLS policy in `supabase/migrations/20260623100000_rls_policies.sql` only checks `org_id = auth_user_org_id()` — it never joins `project_assignments`. Confirmed across all 13 client-visible tables: `projects` (`client_org_read`), `milestones`, `throughput_snapshots`, `teams`, `quality_snapshots`, `quality_error_entries`, `risk_alerts`, `bottlenecks`, `client_communications` (`comms_client_select`), `communication_evidence_links`, `agent_queries`, `agent_query_evidence_links`, `delivery_confidence_scores`.

Impact: any query path that reaches the database *without* going through `scoped_project_query()` / `get_visible_project()` — a new report endpoint, a raw join, an agent's evidence-retrieval query, a future engineer forgetting the helper — will return **every project in the client's org**, not just the ones they're assigned to. This is exactly the failure mode `13. Security & Compliance.md` Rule 1 says RLS exists to prevent ("a bug in application code cannot defeat RLS"); right now a bug in application code *can*.

> **Status: fixed 2026‑07‑13** — `supabase/migrations/20260713100000_client_project_assignment_rls.sql`. See Workstream A below for what changed and what's still assumed rather than confirmed.

**F1a. `communication_evidence_links` and `agent_query_evidence_links` RLS policies referenced a column that doesn't exist — discovered while fixing F1.**
Both tables' `client`- and `delivery_manager`-role policies in `supabase/migrations/20260623100000_rls_policies.sql` filter on `org_id = auth_user_org_id()`, but neither table has an `org_id` column — confirmed against the actual `CREATE TABLE` statements in `supabase/migrations/20260622090000_initial_backend_schema.sql` and the ORM models in `backend/app/db/models/entities.py`. `10. DB Schema.md` itself documented an `org_id` column for both tables ("denormalized for RLS") that was simply never added when the tables were implemented — a spec/implementation drift, not a doc-only error. Since `CREATE POLICY` referencing a nonexistent column raises a hard Postgres error, and migration files typically run inside a transaction, this likely means the *entire* `20260623100000_rls_policies.sql` migration — all 19 Phase‑1 tables' worth of policies — has never successfully applied in any environment where it was run start-to-finish. This could not be verified against a live database in this pass (no local Postgres/Supabase instance was available — see the note at the end of Workstream A), so treat it as a high-confidence static finding, not a runtime-confirmed one, until Workstream C's test harness exists.

> **Status: fixed 2026‑07‑13**, same migration as F1 — the affected policies now join through the parent table (`client_communications` / `agent_queries`) instead of referencing `org_id` directly. `10. DB Schema.md` updated to match the tables as actually implemented.

**F2. `audit_logs` has RLS enabled with zero policies — writes likely fail silently or error.**
`supabase/migrations/20260624120000_audit_logs.sql:15` runs `ALTER TABLE audit_logs ENABLE ROW LEVEL SECURITY` and adds no `CREATE POLICY` at all, in this file or any later migration. Postgres default-denies every operation on an RLS-enabled table with no matching policy. `AuditLogger.log()` (`backend/app/agents/delivery/audit/audit_logger.py:19-35`) and `log_governance_event()` (`backend/app/agents/governance/services/audit_service.py:35`) both write through the caller's own request-scoped, RLS-bound session (not `service_role`) — see them invoked from `backend/app/api/routes/delivery.py:219,252,302` and roughly 15 call sites in `backend/app/agents/governance/services/governance_service.py` and `backend/app/agents/governance/routes/governance.py`. Confirmed call sites span all four roles, not just `delivery_manager`/`super_admin` — `governance.py`'s `READ_ROLES` (which includes `client`) gates the analytics CSV/PDF export routes, both of which call `log_governance_event`. Unless the database role backing normal user connections has `BYPASSRLS` (atypical, and contrary to the security model), every one of these calls is either silently dropped or raising a permission-denied error today.

> **Status: fixed 2026‑07‑13** — `supabase/migrations/20260713110000_audit_logs_rls.sql`. An exhaustive scan across all 67 RLS-enabled tables in this repo (now codified as `backend/tests/test_migrations_rls_policy_coverage.py`, run via `pytest` per `backend/README.md`) confirmed `audit_logs` was the *only* table with this gap — F8's "worth a full pass" concern turned out to be one instance, not a systemic pattern. See Workstream B below for the access-model reasoning and a related, more serious finding (F2a) it surfaced.

**F2a. ⚠ CONFIRMED: the app's live database connection bypasses RLS entirely. Two scheduled jobs also run with no RLS identity — moot today, but will matter once this is fixed.**

> **Confirmed 2026‑07‑13** by connecting read-only to the live database (`aws-0-eu-west-1.pooler.supabase.com`, project `gsmixpaajngxxztgopcs` — the exact `DATABASE_URL` in this repo's `.env`): `SELECT rolbypassrls FROM pg_roles WHERE rolname = current_user` → **`true`**, for the `postgres` role this app connects as. It is not the OS superuser (`rolsuper = false`), but Supabase grants the `postgres` role `BYPASSRLS` by default. **This means every RLS policy in this database — before and after Workstreams A/B — currently has zero effect on the running application.** Tenant isolation today is enforced entirely by application code (JWT-derived `org_id` filters, `scoping.py`'s project-assignment checks) with no database-layer backstop. A bug in any of that application code would not be caught by anything.
>
> The same read-only check also found that the *original baseline* RLS migration (`20260623100000_rls_policies.sql`, predating this plan) had never successfully applied here either — `projects`, `audit_logs`, `client_communications`, and most other tables had **zero** policies of any kind (not even for `delivery_manager`/`bsg_leadership`/`super_admin`). Only `project_assignments` (a separate, later migration file) had its policies live. Root cause matches F1a exactly: the 4 statements referencing the nonexistent `org_id` column on the two evidence-link tables broke the whole batch.
>
> **Fixed 2026‑07‑13** (user-approved, after confirming scope beyond just the 2 new migrations): applied the baseline migration against the live database — skipping only those 4 already-known-broken statements, which Workstream A's migration replaces — then Workstream A's and B's migrations on top. Verified read-only afterward: 244 total policies (up from the pre-existing 4, all on `project_assignments`), `client_has_project_access()` exists, `projects`/`milestones`/`client_communications`/both evidence-link tables each now show the expected 4 policies (client/DM/leadership/super_admin), and `projects.client_org_read` and `communication_evidence_links.comm_evidence_client_select` both show the corrected, project-assignment-aware definitions live. **The database is now fully in sync with the repo's migrations.** The `BYPASSRLS` issue is separate and unresolved — see below.

The original finding, for context on how this was discovered:
Discovered while investigating F2's call sites. `backend/app/main.py`'s weekly cron job (`_scheduled_quality_scan`, `AsyncIOScheduler`, Mondays 02:00) opens a session via `session_scope()` (`backend/app/db/session.py:102` — a context-manager wrapper added since the older checkout this plan started from, which adds a concurrency gate for Supabase's session-pooler client cap but is otherwise just `AsyncSessionLocal()` underneath) and never calls `set_rls_context()`, because there's no JWT to extract one from. In this checkout there's a **second, more frequent instance of the same gap**: `_scheduled_ingestion_queue_poll` (`backend/app/main.py:65`, runs every **30 seconds**) calls `process_ingestion_job_queue()` (`backend/app/services/knowledge_ingestion_jobs.py`), which opens four separate `AsyncSessionLocal()` sessions directly (lines 271, 277, 351, 387) — same gap, much higher frequency. For any of these sessions, `request.jwt.claims` is unset, so `public.current_user_id()`, `public.auth_user_role()`, and `public.auth_user_org_id()` all evaluate to `NULL`. **Now moot in practice** — since the connection bypasses RLS regardless of JWT context, these jobs work fine today. It becomes relevant the moment `BYPASSRLS` is removed: at that point these two jobs would start seeing zero rows and failing every write, with no identity to authorize as. Whatever fixes `BYPASSRLS` needs to also give these jobs a real identity (most likely: keep them on a dedicated `service_role`-equivalent connection that's meant to bypass RLS, rather than the same pool everything else uses).

This is now `13. Security & Compliance.md` §17 item 17, marked highest priority of all open items there. **Not fixed** — removing `BYPASSRLS` from the connection role is a deployment/infrastructure change with real blast radius (every one of these jobs and every RLS-scoped route would suddenly start being subject to policies for the first time), not something to do as a drive-by fix. See "Investigating the `BYPASSRLS` fix" below for what that would actually involve.

**F3. `client_communications` draft ownership doesn't match the documented rule, at both layers.**
`10. DB Schema.md` §7 states, in bold: *"Only the backend service account (`service_role`) may INSERT `client_communications` rows."* In this repo:

### Workstream E — MFA for privileged roles (closes F5, F9 item #2) — **implemented, gated off by default**
1. **Decided 2026‑07‑14.** All three roles: `delivery_manager`, `bsg_leadership`, `super_admin` (matches `13. Security & Compliance.md` §3's original recommendation). Rollout: hard-enforce at login (no soft warning banner, no grace period) — but see step 2's feature flag for how this is made safe to ship without immediately affecting the 514 real users in those roles today.
2. **Done, gated behind a new setting.** Supabase Auth's TOTP MFA is enabled by default on every Supabase project (no dashboard config needed) — this workstream is application-layer only: gate `POST /auth/login` on a verified `aal2` session for in-scope roles, and add the enroll/challenge/verify endpoints Supabase's REST API requires to get there.
   - **`mfa_required_roles` setting** (`backend/app/core/config.py`), comma-separated role values, **empty by default** — MFA enforcement is fully off until this is explicitly set in the real `.env`. This exists because the exact Supabase MFA REST API shape (`POST /auth/v1/factors`, `.../challenge`, `.../verify`) could not be verified against a live sandbox before writing this code (see `app/services/auth.py`'s new methods for what was assumed, sourced from Supabase's documented TOTP guide) — shipping this gated avoids a shape mismatch locking out every in-scope user the moment it merges. **Recommended before enabling for real:** set `MFA_REQUIRED_ROLES` and smoke-test enrollment with one real account (e.g. `pm@bsg.dev`) first.
   - `POST /auth/login`: for in-scope roles, no longer sets cookies immediately. Returns `MfaRequiredRead` (`stage: "enroll"` if no verified TOTP factor exists yet, `"challenge"` if one does) plus a short-lived `pending_token` (the fresh aal1 access token) — never persisted as a session, used only to authenticate the next calls via `Authorization: Bearer`.
   - New endpoints: `POST /auth/mfa/enroll` (returns QR/secret), `POST /auth/mfa/challenge` (fresh challenge per attempt — avoids stale-challenge issues on retry), `POST /auth/mfa/verify` (on success, sets the real auth cookies and completes login — this is the only point a real session is issued for an in-scope role).
   - **Known scope limitation, by design:** only `POST /auth/login` is gated. `POST /auth/refresh` is untouched — an already-issued refresh token keeps working until it naturally expires, so existing active sessions aren't retroactively broken when this is turned on. Matches the user's explicit framing ("hard enforce immediately for **new logins**"), but means enforcement has a long tail for anyone who doesn't log out. Revisit if that's not acceptable.
   - Frontend: `frontend/src/components/auth/MfaStep.tsx` (enrollment QR screen / challenge code screen, converging on one "enter code" step), wired into `login.tsx` and `useAuthStore` (`completeMfaLogin()`, called after verify succeeds).
3. **Done.** `backend/tests/test_auth_mfa.py` (6 tests, all mocked — validates this app's control flow, not Supabase's actual API shape): MFA-required roles get `enroll`/`challenge` responses instead of cookies; out-of-scope roles and empty `mfa_required_roles` are unaffected; the full enroll→challenge→verify flow completes login. ### Workstream I — Stop the app's DB connection from bypassing RLS (closes F2a) — **implemented and validated live 2026‑07‑14, not yet committed/deployed**

**Objective:** make RLS policies actually take effect for the running application, not just exist.

Investigated read-only against the live database on 2026‑07‑13 (no changes made). Findings:

1. This is a standard Supabase project with the usual role set: `anon`, `authenticated`, `authenticator`, `service_role`, `postgres`, `supabase_admin`. Only `postgres`, `service_role`, and `supabase_admin` have `BYPASSRLS`. `anon`, `authenticated`, and — importantly — `authenticator` do **not**.
2. `authenticated` already has full `SELECT`/`INSERT`/`UPDATE`/`DELETE` grants on every table checked (`projects`, `users`, `organisations`, `audit_logs`) and `EXECUTE` on all four RLS helper functions (`auth_user_role`, `auth_user_org_id`, `current_user_id`, `client_has_project_access`). This is Supabase's default provisioning — **no new grants need to be created**, they're already there and unused.
3. The current connection role, `postgres`, already has membership (with `ADMIN OPTION`) to `SET ROLE` into `authenticated`, `anon`, or `service_role`. So does `authenticator`.

**Implemented 2026‑07‑14** (after explicit, separate user sign-off — the two earlier decisions below covered *what* the fix should look like, not *whether to actually run it against the live database*; that needed its own confirmation, requested and given): `backend/app/db/rls.py`'s `set_rls_context()` now runs `SET LOCAL ROLE authenticated` immediately after the existing `set_config('request.jwt.claims', ..., true)` call — exactly the fix researched above. `SET LOCAL` is transaction-scoped, matching the `is_local=true` on the existing `set_config` call, so both revert automatically at transaction end (this app pools and reuses physical connections, so a plain non-`LOCAL` `SET ROLE` would have leaked across requests on a reused connection).

For the scheduled jobs (F2a) that have no per-user JWT at all: **decided 2026‑07‑14 (user-approved)** — keep them on an explicit bypass rather than a real synthetic identity. **Implemented**: `_scheduled_quality_scan` (`backend/app/main.py`) and all four `AsyncSessionLocal()` sessions in `process_ingestion_job_queue`/`run_knowledge_ingestion_job` (`backend/app/services/knowledge_ingestion_jobs.py`) now call a new `set_service_role_context()` helper (`backend/app/db/rls.py`), which runs `SET LOCAL ROLE service_role`. This changes nothing about current behavior (both jobs already operate across every org today) — the bypass is now explicit and auditable instead of an accidental side effect of the shared connection role's `BYPASSRLS`.

**A second blocker, found and fixed 2026‑07‑14 while finishing Workstream C step 2: F10 / BUG-007.** `communication_evidence_links` and `agent_query_evidence_links` had no INSERT policy for any role, in any migration — confirmed live, then fixed the same day (user-approved): `supabase/migrations/20260714100000_evidence_links_insert_rls.sql`. See `docs/18. Known Bugs.md` BUG-007.

**Validated live, 2026‑07‑14** (explicit user sign-off requested and given for this specific step, after the platform's permission system itself flagged that running a test against the live database with this change active needed its own authorization beyond the two prerequisite decisions): `backend/tests/rls/test_set_rls_context_live.py` calls the *actual*, unmodified `set_rls_context()` function — not a hand-rolled mirror of it, unlike every other test in `backend/tests/rls/` — against a session opened the same way a real request does (`session_scope()`), and confirms an assigned client sees only their project, an unassigned client sees nothing, and a delivery_manager sees their whole org. All 3 passed. Combined with the rest of Workstream C's suite (54 more tests, all passing with this change active), that's the closest this repo's architecture allows to a "staging-equivalent smoke test" — there is no environment separate from this live database to test against instead.

**What "done" does and doesn't mean here:** the code change is written, applied to this working tree, and proven correct for the scenarios above against the real database. It is **not yet committed to git or deployed** — if this repo is running anywhere separate from this local checkout (a staging or production deployment this plan hasn't had visibility into), this change has no effect there until it's committed, reviewed, and deployed through whatever process that environment uses. Recommended before merging: run the full live-RLS suite one more time (`pytest --run-live-rls tests/rls`, ~57 tests) as a final check, and have a second person review `rls.py`'s change specifically, given its blast radius.
