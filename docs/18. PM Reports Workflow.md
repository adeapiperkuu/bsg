# PM Reports Workflow & Client Archive

> Controlled client communications for the BSG Operations Tower.
> Covers the PM `/reports` workflow console and the client `/client/reports` published archive.

---

## 1. Purpose

The PM Reports workflow converts delivery, quality, risk, and project evidence into controlled client communications.

AI may draft; humans must review, approve, and explicitly send. Clients only ever see **sent** reports.

---

## 2. Product separation

| Route | Audience | Purpose |
| --- | --- | --- |
| `/reports` | PM / internal | Full communication lifecycle |
| `/client/reports` | Client | Sent-only, read-only archive |

PM statuses: `draft`, `in_review`, `approved`, `sent`, `rejected`  
Client statuses: `sent` only

---

## 3. Managed areas

```text
A. Report inbox          — org-scoped lightweight list + filters
B. Report workspace      — lazy detail, edit, lifecycle actions, evidence
C. Generate dialog       — project + type + subject + instructions → one POST
D. Lifecycle & permissions — review / approve / reject / send (distinct)
E. Client archive        — sent-only list + read-only detail
```

---

## 4. Architecture

```text
PM /reports
→ GET  /communications
→ GET  /communications/{id}
→ POST /projects/{id}/communications/draft
→ PATCH /communications/{id}              (save edits)
→ PATCH /communications/{id}/review
→ POST  /communications/{id}/approve
→ POST  /communications/{id}/reject
→ POST  /communications/{id}/send

Client /client/reports
→ GET /client/communications              (sent list, no bodies)
→ GET /communications/{id}                (sent-only for CLIENT; sanitized)
```

### Ownership

**Frontend**
- list rendering, filters, selection, dialog form
- lazy detail, editor, lifecycle actions, permission-driven controls
- client archive UI (read-only)

**Backend**
- organization/project scoping
- list query, evidence gathering, LLM generation, fallback
- persistence, transition validation, client visibility

**Agent involvement**
- Frontend talks only to the communications backend
- Backend invokes the Client Interaction Agent path and reads evidence from Delivery Performance, Quality Intelligence, and authorized project sources
- Frontend must **not** call `/agent-queries` for report generation

---

## 5. State machine

```text
draft ──edit──► draft
  │
  ├──submit review──► in_review ──edit──► in_review
  │                      │
  ├──approve─────────────┼──approve──► approved ──send──► sent
  │                      │
  └──reject──────────────┴──reject──► rejected ──Generate new──► (new draft)
```

Invalid transitions → `409 INVALID_COMMUNICATION_TRANSITION`.

Approve and Send are **always separate**. Approved-but-unsent reports are never client-visible.

## 6. Permission matrix

| Role | `/reports` | Generate / edit / review / approve / reject / send | `/client/reports` |
| --- | --- | --- | --- |
| `delivery_manager` | full | yes (`can_approve_communications`) | no |
| `super_admin` | full | yes | no |
| `bsg_leadership` | read-only | no | no |
| `client` | no | no | sent archive only |

Backend role gates remain authoritative for every mutation.

---

## 7. Query rules

### Inbox (`GET /communications`)
- one list request; no project fan-out; no bodies
- bounded evidence-count aggregation; stable `created_at DESC` ordering
- indexes: `(org_id, created_at DESC)`, evidence `(communication_id)`

### Client archive (`GET /client/communications`)
- sent-only; org-scoped; no bodies; no status override
- index: `(org_id, status, sent_at DESC, created_at DESC)`

### Workspace
- one detail request when selected
- generation response seeds detail cache (no redundant fetch)

### Generate
- one synchronous POST; no polling; no frontend agent/Delivery/Quality calls

---

## 8. Explicit non-goals

- no background generation
- no polling
- no automatic sending or approval
- no full bodies in inbox list
- no fan-out per project
- no coupling to Governance weekly-summary jobs
- no merged PM/client route
