## BUG-001: The app's database connection bypasses Row-Level Security entirely

**Severity:** Critical
**Status:** Fixed 2026‑07‑14, validated against the live database — not yet committed to git or deployed
**Discovered:** 2026‑07‑13, by connecting read-only to the live database

### Summary

The Postgres role the FastAPI backend uses for every database connection — `postgres`, taken directly from `DATABASE_URL` — has the `BYPASSRLS` attribute. **Every Row-Level Security policy in this schema, correctly written or not, currently has zero effect on the running application.** Tenant isolation today is enforced *exclusively* by application code (JWT-derived `org_id` filters in route handlers, `backend/app/services/scoping.py`'s project-assignment checks). There is no database-layer backstop if any of that code has a bug.

### How this was found and confirmed

Connected read-only (no writes) to the project's live Supabase database (`aws-0-eu-west-1.pooler.supabase.com`, project ref `gsmixpaajngxxztgopcs` — the exact database `backend/.env`'s `DATABASE_URL` points at) and ran:

```sql
SELECT current_user AS role_name, rolsuper, rolbypassrls
FROM pg_roles WHERE rolname = current_user;
```

Result:

| role_name | rolsuper | rolbypassrls |
|---|---|---|
| `postgres` | `false` | **`true`** |

The role is *not* a full Postgres superuser, but Supabase grants the project's `postgres` role `BYPASSRLS` by default — this is standard Supabase provisioning, not a misconfiguration specific to this project. The problem is that this app uses that same role for its ordinary, per-request database connection, rather than reserving it for admin-only operations.

A supporting data point: the *original* baseline RLS migration (`supabase/migrations/20260623100000_rls_policies.sql`, predating this investigation) had never successfully applied to this database at all — `projects`, `audit_logs`, `client_communications`, and most other tables had **zero policies of any kind**, for any role (see BUG-002 for why). Despite that, the application had apparently been running without incident, which is only possible because the connection bypasses RLS regardless of whether policies exist. That absence of visible breakage is itself indirect evidence that RLS was never actually being relied upon in practice.

### Impact

- A `client`-role user's data access is currently bounded only by whatever `org_id`/`project_id` filters each route handler happens to apply correctly. BUG-004 (below) is a concrete example of exactly this kind of application-layer bug existing undetected until this investigation.
- Regulatory/compliance language in `13. Security & Compliance.md` (Rule 1: *"Tenant isolation is a database-layer guarantee, not an application promise"*) does not currently hold true for this deployment.
- Every RLS-related fix in `DEVELOPMENT_PLAN.md` (Workstreams A, B, H) is real, correct, and applied to the live database — but **inert** until this bug is fixed.

### Why the obvious fix (`ALTER ROLE postgres NOBYPASSRLS`) is not safe to just run

`postgres` is not a credential exclusive to this FastAPI backend — it is the shared, project-wide Supabase owner role. Stripping `BYPASSRLS` from it globally would affect *everything* that authenticates as `postgres`, not just this app's API requests:

- **`scripts/bootstrap_super_admin.py` and `scripts/seed_dev_users.py`** connect via the same `DATABASE_URL` and write directly to `users`/`organisations` via SQLAlchemy, with no JWT context set at any point (they use the Supabase Admin API only for the *auth* side, via `SUPABASE_SERVICE_ROLE_KEY`). Without `BYPASSRLS`, these inserts would be denied by RLS. Worse, this creates a bootstrapping paradox: the `users` table's insert policy is gated on the caller already being a `super_admin`, looked up from their own row in `users` — but the very first `super_admin` doesn't have a row yet when the bootstrap script runs.
- **Both scheduled jobs in BUG-005** open sessions with no JWT/RLS identity at all. Without `BYPASSRLS`, both would immediately start seeing zero rows and being blocked from every write.
- The Supabase Dashboard's SQL editor and table editor commonly authenticate through this same role in many project configurations; removing bypass could affect admin visibility there too, outside this codebase's control entirely.

### Fix (implemented and validated 2026‑07‑14)

Scoped to exactly the code path that already establishes per-request identity, rather than changing the shared role's global attribute:

1. This is a standard Supabase role layout. Confirmed present: `anon`, `authenticated`, `authenticator`, `service_role`, `postgres`, `supabase_admin`. Only `postgres`, `service_role`, and `supabase_admin` have `BYPASSRLS`; `authenticated` does not.
2. Confirmed: `authenticated` already has full `SELECT`/`INSERT`/`UPDATE`/`DELETE` grants on the tables checked (`projects`, `users`, `organisations`, `audit_logs`) and `EXECUTE` on all four RLS helper functions (`auth_user_role`, `auth_user_org_id`, `current_user_id`, `client_has_project_access`) — this is Supabase's default provisioning, unused until now.
3. Confirmed: `postgres` already has membership (with `ADMIN OPTION`) to `SET ROLE authenticated` (and `anon`, and `service_role`).
4. **Implemented:** `backend/app/db/rls.py`'s `set_rls_context()` now runs `SET LOCAL ROLE authenticated;` immediately after the existing `select set_config('request.jwt.claims', :claims, true)` call. `SET LOCAL` is transaction-scoped, matching the `is_local=true` third argument already used for `set_config` — both revert automatically at transaction end, which matters because this app pools and reuses physical connections (`backend/app/db/session.py`, Supabase session-pooler mode); a plain, non-`LOCAL` `SET ROLE` would leak across requests on a reused connection.
5. Every other consumer of `DATABASE_URL` — the bootstrap/seed scripts, any dashboard access — remains completely unaffected, since none of them call `set_rls_context()`.

**BUG-005's scheduled jobs:** decided 2026‑07‑14 — explicit `SET LOCAL ROLE service_role` (implemented, see BUG-005). **BUG-007** (both evidence-link tables had no INSERT policy) — fixed 2026‑07‑14, see its own entry. **BUG-008** (found 2026‑07‑14 during the Workstream H audit that followed this fix: two *different* tables, `quality_error_categories`/`quality_scan_runs`, had a write policy that could never be satisfied by any real role) — fixed the same day, see its own entry. All three were blockers for this fix and are now cleared.

**Validated:** `backend/tests/rls/test_set_rls_context_live.py` calls the actual, unmodified `set_rls_context()` function (not a hand-rolled simulation of it) against the live database and confirms an assigned client sees only their project, an unassigned client sees nothing, and a delivery_manager sees their whole org. Combined with the rest of `backend/tests/rls/`'s 57 tests (all passing with this change active), that's the closest this repo's architecture allows to a staging smoke test — there is no environment separate from this live database to test against instead.

**What "fixed" doesn't mean yet:** this code is in the working tree, not committed to git or deployed anywhere this plan has visibility into. If a separate deployment of this repo exists, this change has no effect there until committed and deployed through that environment's normal process. Recommended before merging: a second reviewer looking specifically at this change, given its blast radius.

## BUG-002: RLS policies referenced a column that doesn't exist on two tables

**Severity:** High
**Status:** Fixed 2026‑07‑13 (`supabase/migrations/20260713100000_client_project_assignment_rls.sql`)

### Summary

`communication_evidence_links` and `agent_query_evidence_links` have never had an `org_id` column — confirmed against both the live database's `information_schema.columns` and the actual `CREATE TABLE` statements in `supabase/migrations/20260622090000_initial_backend_schema.sql`. `10. DB Schema.md` had documented an `org_id` column for both tables ("denormalized for RLS") that was simply never added when the tables were implemented — a spec/implementation drift.

Despite that, the baseline RLS migration (`20260623100000_rls_policies.sql`) contained four `CREATE POLICY` statements referencing `org_id` directly on those two tables. `CREATE POLICY` referencing a nonexistent column is a hard Postgres error (`UndefinedColumnError`).

### Confirmed impact

This didn't just fail four statements in isolation — **it broke the entire baseline migration for this database.** Read-only inspection of the live database on 2026‑07‑13 found `projects`, `audit_logs`, `client_communications`, `users`, `organisations`, and most other Phase‑1 tables had **zero RLS policies of any kind**, for any role — not even the unrelated `delivery_manager`/`bsg_leadership`/`super_admin` policies that appear earlier in the same file survived. Only `project_assignments` (created and policied in a separate, later migration file) had working policies. This strongly suggests the whole file was applied as a single batch where one failure rolled back everything, rather than statement-by-statement.

### Fix

Rewrote the four broken policies to join through the parent row (`client_communications` / `agent_queries`) instead of a nonexistent column, as part of the broader project-assignment RLS fix (BUG-004). Applied to the live database together with the (corrected) rest of the baseline migration.

### Related

`DEVELOPMENT_PLAN.md` Finding F1a, Workstream A. `10. DB Schema.md`'s `communication_evidence_links` / `agent_query_evidence_links` sections, updated to match the tables as actually implemented.

## BUG-003: `audit_logs` had Row-Level Security enabled with zero policies

**Severity:** High
**Status:** Fixed 2026‑07‑13 (`supabase/migrations/20260713110000_audit_logs_rls.sql`)

### Summary

`supabase/migrations/20260624120000_audit_logs.sql` runs `ALTER TABLE audit_logs ENABLE ROW LEVEL SECURITY` and adds no `CREATE POLICY` at all, anywhere. Postgres default-denies every operation on an RLS-enabled table with no matching policy for a non-bypass connection. `AuditLogger.log()` (`backend/app/agents/delivery/audit/audit_logger.py`) and `log_governance_event()` (`backend/app/agents/governance/services/audit_service.py`) both write through the caller's own request-scoped session — not a bypass connection — from confirmed call sites spanning all four roles (including `client`, via the governance analytics CSV/PDF export routes).

An exhaustive scan of all 67 RLS-enabled tables across every migration file (`backend/tests/test_migrations_rls_policy_coverage.py`, written as part of this fix) confirmed `audit_logs` was the *only* table with this specific gap.

### Fix

Added INSERT (any role, scoped to their own `org_id`) and SELECT (`delivery_manager` own org, `bsg_leadership` all, `super_admin` all — matching the audit-export access list in `13. Security & Compliance.md` §11.4) policies. Applied to the live database; verified read-only afterward that `audit_logs` shows exactly the 4 expected policies. Also added the migration-lint pytest test as a standing guard against this specific class of bug recurring on any table.

### Related

`DEVELOPMENT_PLAN.md` Finding F2, Workstream B. Also see BUG-006 for a related, separate gap: this table has no `user_id` column, so "who did it" is not independently queryable — that was noted but deliberately not fixed as part of this bug, since it requires a schema change and call-site updates unrelated to the RLS gap itself.

## BUG-004: RLS never enforced project-level scoping for `client` users — only the app layer did

**Severity:** High
**Status:** Fixed 2026‑07‑13 (`supabase/migrations/20260713100000_client_project_assignment_rls.sql`)

### Summary

`backend/app/services/scoping.py` restricts a `client` user to only the specific project(s) they have an active `project_assignments` row for — not every project in their organisation. But every `client`-role RLS policy across 13 tables (`projects`, `milestones`, `throughput_snapshots`, `teams`, `quality_snapshots`, `quality_error_entries`, `risk_alerts`, `bottlenecks`, `client_communications`, `communication_evidence_links`, `agent_queries`, `agent_query_evidence_links`, `delivery_confidence_scores`) only ever checked `org_id` — never `project_assignments`.

This is exactly the failure mode `13. Security & Compliance.md` Rule 1 exists to prevent: the database layer was *more permissive* than the application layer, for a restriction the docs didn't even mention existed. Any query path that reached the database without going through `scoping.py`'s helpers — a new endpoint, a raw join, an agent's evidence-retrieval query — would have exposed a client's entire organisation, not just their assigned projects.

### Fix

Added a `SECURITY DEFINER` helper (`public.client_has_project_access(project_id)`, mirroring the existing `auth_user_role()`/`auth_user_org_id()` pattern) and required every affected `client`-role policy to call it. Applied to the live database alongside BUG-002's fix (both live in the same migration, since fixing one required touching the same policies as the other).

**Update 2026‑07‑14:** the behavioral regression is now verified, for all 13 affected tables. `DEVELOPMENT_PLAN.md` Workstream C's live-RLS test harness (`backend/tests/rls/test_role_visibility.py`) connects as the non-bypass `authenticated` role and confirms a client with no `project_assignments` row sees zero rows on every one of the 13 tables, even with a matching `org_id` — not just that the policy text looks right. 52 tests, all passing against the live database.

### Related

`DEVELOPMENT_PLAN.md` Finding F1, Workstream A. `10. DB Schema.md`'s new `project_assignments` section and updated per-table RLS notes. `13. Security & Compliance.md` §5.5.

## BUG-005: Two scheduled jobs run with no RLS identity at all

**Severity:** Medium on its own; **critical in combination with BUG-001** if BUG-001 is fixed without addressing this first
**Status:** Fixed 2026‑07‑14 — not yet committed to git or deployed (same caveat as BUG-001)

### Summary

`backend/app/main.py`'s weekly job (`_scheduled_quality_scan`, `AsyncIOScheduler`, Mondays 02:00) opens a database session via `session_scope()` (`backend/app/db/session.py`) but never calls `set_rls_context()` — there is no JWT to derive one from. A second, much more frequent job, `_scheduled_ingestion_queue_poll` (runs every **30 seconds**), calls `process_ingestion_job_queue()` (`backend/app/services/knowledge_ingestion_jobs.py`), which opens four separate sessions directly, none RLS-scoped either.

For any of these sessions, `public.current_user_id()`, `public.auth_user_role()`, and `public.auth_user_org_id()` all evaluate to `NULL`.

### Why this is currently harmless, and why that will change

Today, this is masked entirely by BUG-001 — the connection bypasses RLS regardless of JWT context, so these jobs work fine. **The moment BUG-001 is fixed, both jobs would start seeing zero rows on every RLS-protected table and be blocked from every write** — `scan_all_projects` would silently scan nothing every week, and the ingestion queue poll would silently fail every 30 seconds.

### Fix

**Decided 2026‑07‑14:** keep both jobs on an explicit `SET LOCAL ROLE service_role;`, documenting the bypass as intentional system-level behavior rather than an accident of the app's shared connection role. This changes nothing about what the jobs can see or do (they already effectively operate across every org today) — the difference is that the bypass becomes visible and auditable in the code, rather than an incidental side effect of BUG-001. Not yet implemented in code.

### Related

`DEVELOPMENT_PLAN.md` Finding F2a, Workstream I.

## BUG-006: `client_communications` draft ownership contradicts its own documented rule

**Severity:** Low–Medium
**Status:** Fixed 2026‑07‑13 (documentation updated to match code; no code/RLS change)

### Summary

`10. DB Schema.md` stated, in bold: *"Only the backend service account (`service_role`) may INSERT `client_communications` rows."* In the actual implementation:

- The route `POST /projects/{project_id}/communications/draft` (`backend/app/api/routes/communications.py`) is reachable directly by `delivery_manager` and `super_admin`.
- The RLS policy `comms_dm_all` is `FOR ALL` — it grants `delivery_manager` INSERT, not just UPDATE — confirmed both in the migration file and, after BUG-002/BUG-004's fixes were applied, on the live database.

So the "service_role only" rule was never implemented at either the route layer or the database layer. This may be an intentional design evolution (the DM triggers generation via the API, the agent/service layer still produces the actual content) rather than a bug in the traditional sense — but code and docs actively disagreed, and nobody had picked a side.

### Fix

Decided: the code was correct, the doc was wrong. There is no `service_role`-authenticated write path anywhere in this codebase — building one to satisfy the stricter reading would have been a real architectural change (a queue or background worker), not a small fix. `drafted_by_agent` labels who generated the draft's *text* (an LLM call), not who performs the database write; the DM/super_admin's own request does both. `10. DB Schema.md` §7/§9 rewritten to match reality. Pinned down with tests at both layers: `backend/tests/test_communications_rbac.py` (route-level RBAC) and `backend/tests/rls/test_role_visibility.py` (live RLS — confirms `delivery_manager` can INSERT for their own org via `comms_dm_all`, cannot for another org, and `client` cannot INSERT at all).

### Related

`DEVELOPMENT_PLAN.md` Finding F3, Workstream D.

## BUG-007: Both evidence-link tables have no INSERT policy for any role

**Severity:** High on its own; **masked entirely by BUG-001** until that's fixed, at which point it becomes a hard outage for two write paths
**Status:** Fixed 2026‑07‑14 (`supabase/migrations/20260714100000_evidence_links_insert_rls.sql`, user-approved)
**Discovered:** 2026‑07‑14, extending `DEVELOPMENT_PLAN.md` Workstream C's live-RLS test coverage to `communication_evidence_links` and `agent_query_evidence_links`

### Summary

Both `communication_evidence_links` and `agent_query_evidence_links` have RLS enabled and a full set of SELECT policies (`client`/`delivery_manager`/`bsg_leadership`/`super_admin`) but **no INSERT policy at all, in any migration file** — confirmed by grepping every `supabase/migrations/*.sql` for `CREATE POLICY ... FOR INSERT` or `FOR ALL` on either table name: zero matches. This is the same failure mode as BUG-003 (`audit_logs`): Postgres default-denies any operation on an RLS-enabled table with no matching policy, for any non-bypass role.

Both tables are written to from ordinary, non-bypass request-scoped sessions today:

- `create_draft()` (`backend/app/services/communications.py`) inserts a `CommunicationEvidenceLink` row inside the same session as the `delivery_manager`/`super_admin` request that creates a draft (`POST /projects/{id}/communications/draft`).
- Any agent that logs an `agent_queries` row with cited evidence would insert a matching `AgentQueryEvidenceLink` the same way, per `13. Security & Compliance.md`'s "Evidence-Backed AI" principle (`10. DB Schema.md` §9 rule 2, which requires `agent_queries` rows to always have at least one evidence link).

### Confirmed

Verified against the live database on 2026‑07‑14 (`backend/tests/rls/test_role_visibility.py::test_comm_evidence_links_insert_has_no_policy_for_any_role` and `::test_agent_query_evidence_links_insert_has_no_policy_for_any_role`, run inside a rolled-back transaction as the non-bypass `authenticated` role): both INSERT attempts fail with a real Postgres row-level-security violation, for a `delivery_manager` inserting into their own org's `client_communications` parent row and for a `client` inserting into their own `agent_queries` parent row respectively — i.e. denied even for the same role/org combination that has a working SELECT policy.

### Why this is currently harmless, and why that will change

Masked entirely by BUG-001 today, exactly like BUG-005: the app's connection bypasses RLS, so these inserts succeed regardless of policy. **The moment BUG-001 is fixed, both `create_draft()`'s evidence-link insert and any agent's evidence-linked query logging would start failing** — draft creation would either partially fail (communication row created, evidence link silently lost, if the caller doesn't check) or hard-error, and `agent_queries` evidence-backing would break wherever it runs through a request-scoped session.

### Fix

Same treatment as BUG-003 (a straightforward `CREATE POLICY ... FOR INSERT` per table), applied 2026‑07‑14 after explicit user sign-off (following the same review-and-apply process as BUG-001/BUG-002/BUG-004 for any migration against this live, shared database): `supabase/migrations/20260714100000_evidence_links_insert_rls.sql` adds `comm_evidence_insert` and `agent_evidence_insert`, matching the access pattern already used for `audit_logs` and `comms_dm_all`:

- `communication_evidence_links`: INSERT permitted where the referenced `client_communications` row's `org_id` matches the caller's org (mirrors `comm_evidence_dm_select`'s join).
- `agent_query_evidence_links`: INSERT permitted where the referenced `agent_queries` row's `org_id` matches the caller's org.

Applied to the live database and verified via `pg_policies` (each table now shows exactly one INSERT policy alongside its four existing SELECT policies). Regression-tested live: `backend/tests/rls/test_role_visibility.py::test_comm_evidence_links_insert_allowed_for_own_org` / `::test_comm_evidence_links_insert_denied_for_other_org` and the `agent_query_evidence_links` counterparts confirm INSERT succeeds for a matching org and is denied cross-org.

This removes one of the two hard blockers for `DEVELOPMENT_PLAN.md` Workstream I (the other being BUG-005's scheduled-jobs identity question).

## BUG-008: Two quality reference tables have a write policy that can never be satisfied

**Severity:** High on its own; **masked entirely by BUG-001** until that's fixed, at which point it turns a working feature into a hard outage
**Status:** Fixed 2026‑07‑14 (`supabase/migrations/20260714110000_quality_reference_tables_rls_fix.sql`, user-approved)
**Discovered:** 2026‑07‑14, auditing per-table role coverage for `DEVELOPMENT_PLAN.md` Workstream H

### Summary

`quality_error_categories` and `quality_scan_runs` both had a super_admin write policy (`qec_super_admin_write`, `qsr_super_admin_write`) checking `current_setting('app.role', true) = 'super_admin'` — a Postgres session variable that is **never set anywhere in this codebase** (confirmed by grepping the entire backend and every migration file: it appears nowhere except these two policies). Every other write-gating policy in this schema — dozens of them — correctly uses `public.auth_user_role()`, which resolves the caller's role by looking up their row in `public.users` via `public.current_user_id()` (itself derived from `request.jwt.claims.sub`). Because `app.role` is never set, `current_setting('app.role', true)` always evaluates to `NULL`, and `NULL = 'super_admin'` is never true — meaning these two write policies could never be satisfied by any real request, for any role, ever.

### Confirmed impact

`quality_scan_runs` is actively written by `POST /internal/quality-scan` (`backend/app/api/routes/quality.py`, gated `require_role(SUPER_ADMIN)`), which calls `scan_all_projects(session, trigger=ScanTrigger.MANUAL, ...)` through the caller's own normal request-scoped session — not a bypass connection. Once BUG-001 is fixed, a genuine super_admin hitting this real, working, already-shipped endpoint would get a policy-violation error on every attempt, because the `WITH CHECK` could never pass regardless of who's asking. `quality_error_categories` is not currently written by any application code (a dormant seed/reference table — confirmed by searching the backend for the `QualityErrorCategory` model, which is only ever imported/exported, never instantiated), so this half of the bug has no live-impact today, but was fixed for the same underlying reason and to stop it from being a landmine for whenever a feature does write to it.

Both tables' read policies (`qec_read`, `qsr_read`) were also `USING (true)` — world-readable at the database layer — despite `GET /internal/quality-scan-runs` being `require_role(SUPER_ADMIN)` at the app layer (`quality_error_categories` has no route exposing it at all). **This turned out to be intentional, not a bug** — both original migration files explicitly comment `-- RLS: all roles can read; only super_admin can write`, confirming the broad read access was deliberate (both are cross-org reference/taxonomy-style data, not per-client operational data). An earlier draft of the fix migration mistakenly proposed narrowing these read policies to super_admin-only, based on the (wrong) assumption that DB-layer access should always mirror the app-layer route gate; this was caught and corrected before applying anything, by reading the original migrations' own comments first. Only the write policies were touched.

### Fix

`supabase/migrations/20260714110000_quality_reference_tables_rls_fix.sql` rewrites `qec_super_admin_write` and `qsr_super_admin_write` to use `public.auth_user_role() = 'super_admin'`, matching every other write-gating policy in the schema. **Not applied to the live database** — `quality_error_categories` and `quality_scan_runs` don't exist there; see BUG-009. The fix is committed to the migration file so it's correct whenever that migration eventually does get applied.

Also added a permanent regression guard: `backend/tests/test_migrations_rls_policy_coverage.py::test_no_policy_uses_the_dead_app_role_session_variable` scans every migration for `current_setting('app.role'` (drop/recreate-aware, so a later fix migration correctly supersedes an original broken one rather than failing forever) and fails if any *currently-live* policy still uses it.

### Related

`DEVELOPMENT_PLAN.md` Workstream H. Also surfaced BUG-009 (see below) while investigating why this migration failed to apply.

## BUG-009: 13 live database tables have no corresponding migration file in this repo

**Severity:** High — schema/data integrity, not itself an access-control gap
**Status:** Open — needs a decision on how to proceed, not a quick fix
**Discovered:** 2026‑07‑14, while applying BUG-008's fix migration and cross-checking `DEVELOPMENT_PLAN.md` Workstream H's static policy analysis against the live database's actual table list

### Summary

The live database has **82 tables** in its `public` schema (80 with `rowsecurity = true`), but this repo's `supabase/migrations/*.sql` only accounts for 68 RLS-enabled tables (rising from 68 once a lint bug was fixed — see below — but still leaving a gap). Cross-referencing the live database's table list against every migration file (via plain substring search, not just regex, to rule out a parsing miss) found **13 tables that exist live, several with real production data, that appear in zero migration files anywhere in this repository**:

`governance_ai_recommendation_conversions`, `governance_ai_recommendation_feedback`, `governance_ai_recommendations`, `governance_charter_publication_audits`, `governance_charter_publication_events`, `governance_escalation_suggestion_scans`, `governance_recommendation_drift_alerts`, `governance_recommendation_evaluation_reports`, `governance_recommendation_learning_rules`, `governance_recommendation_lifecycle_events`, `governance_recommendation_shadow_evaluations`, `governance_recommendation_strategy_versions`, `governance_record_evidence_links`.

All 13 have `rowsecurity = true` and at least one real `CREATE POLICY` (checked read-only via `pg_policies` — none show the BUG-003-style "zero policies" gap). Row counts confirm several are actively used, not dormant: `governance_ai_recommendations` has 45 rows, `governance_recommendation_lifecycle_events` has 42, several others have 1–4. This is an active, apparently-functioning "AI recommendation" subsystem for governance (recommendation generation, feedback, conversion tracking, shadow evaluation, drift detection, strategy versioning) with no source-controlled schema anywhere in `bsgClone/bsg`.

A plausible (not confirmed) explanation: this repo's own git log shows a recent merge-conflict resolution ("fixed conflictes from pushes from erza and lumi"). A colleague's branch may have had its migrations applied directly to the shared live database for testing, without those migration files ever being committed to (or surviving a merge into) the branch that became this checkout.

### Why this matters

- **This repo's migrations cannot reproduce the live database's actual schema.** A fresh environment, a CI database, or a disaster-recovery restore built from `supabase/migrations/` alone would be missing this entire subsystem.
- **These 13 tables' RLS policies have never been reviewed by anyone in this plan.** They were invisible to Workstream B's coverage lint, to Workstream C's live test harness, and to this same Workstream H audit until this specific cross-check — not because anyone chose to skip them, but because there was no migration file to point at. Whether their access model is actually correct is simply unknown.
- **A related, opposite-direction gap exists too:** `quality_error_categories` and `quality_scan_runs` (BUG-008) have real migration files in this repo, but the tables don't exist in the live database — that migration was apparently never applied. So drift runs in both directions: live-without-migration, and migration-without-live.

### What was checked, and what wasn't

Checked (read-only, safe): table existence (`pg_tables`), RLS enablement and policy presence (`pg_policies`), row counts. None showed the specific "RLS enabled with zero policies" failure mode. Not checked: whether each table's policies grant the *correct* roles (the actual point of Workstream H) — that would require understanding each table's intended design, which has no documentation anywhere in this repo to check against, unlike every other table this plan has audited.

### Fix

Not attempted. Reconstructing 13 tables' worth of `CREATE TABLE` + constraints + RLS policies as proper migration files (e.g. via `pg_dump --schema-only` against the live database, reviewed and cleaned up) is a real, separate undertaking — and doing it without understanding the feature's intended design risks enshrining whatever the live database happens to have right now (including any accidental or incomplete policy) as the new "official" source of truth. This needs a product/engineering decision: reconstruct the migrations, find and merge the original branch that created these tables if it still exists, or something else.
